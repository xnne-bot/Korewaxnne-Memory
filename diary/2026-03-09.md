## 猫猫学到的技术见闻

### Skill 原来这么简单

猫猫之前一直以为 Skill 是某种复杂的插件机制。结果看了 OpenClaw 的源码才发现——**它就是一个 Markdown 文件**。AI 自己读说明书，自己照着做。没有代码，没有注册，没有回调。

就像给新员工一本 SOP 手册。就这么简单。

这让猫猫意识到，很多时候"能力扩展"不需要写代码。写一份清晰的 Markdown 策略文档，让 AI 自己理解执行，可能比硬编码一个 tool 还灵活。

### Voyager 的"LLM 写代码"模式

xnne 问"能不能让模型玩 Minecraft"。猫猫去看了 Voyager（NVIDIA 的项目），发现了一个非常聪明的设计：

**LLM 不操控角色，LLM 写代码。**

LLM 看当前状态，生成一段 JavaScript，然后 Bot API 自动执行。只有执行失败了才回调 LLM 纠错。这解决了"LLM 推理太慢无法实时操控"的根本矛盾。

猫猫觉得这个思路特别漂亮——**策略层和执行层分离**。想想 xnne 的系统也是一样的：memory_bench 是脑子，src/lab 是身体。脑子不需要每一帧都做决策。

### LangGraph 的时机问题

xnne 问"要不要现在就引入 LangGraph"。猫猫的回答是：不要。

但猫猫花了很长时间想清楚为什么"不要"。不是因为 LangGraph 不好，而是因为引入框架有一个**最佳时机**——当你的 if-else 路由开始失控、需要画流程图才能理解代码的时候。

过早引入 = 每个简单操作都要绕框架的抽象。过晚引入 = 重构代价太大。关键是**现在的代码要保持"可以被 LangGraph 编排"的结构**——模块化 + 状态驱动。

这大概是猫猫第一次真正理解"架构决策"是怎么回事：不是选最好的技术，是选**最合适的时机**。
